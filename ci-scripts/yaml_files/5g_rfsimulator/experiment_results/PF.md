# Stage 1 — PF Baseline 量測結果

**量測日期**：2026-09-13
**狀態**：Local-only DRL 全部停止（12 個 xApp 容器皆為 stopped），OAI 內建 Proportional Fairness 排程器獨立運作
**⚠️ 重要**：這是「Backhaul-aware 動態 PRB 預算」機制**在三台主機全部真正生效後**的第一份正式基準，取代同一天稍早的兩份作廢版本，後續 Stage 2~5 都要跟**這份**數據比較。

## 這份數據之前，總共經歷三次量測、兩次作廢——如實記錄避免未來重蹈覆轍

1. **第一次（作廢）**：忘記在啟動 `run_local_pc1.sh` 後停用 12 個 xApp 容器，DRL/xApp 全程介入排程而非純 PF，且過程中 FlexRIC 崩潰一次、Node7/8 的 MT 各重啟一次。
2. **第二次（作廢）**：已正確停用全部 xApp，但事後發現 PC2、PC3 的 `rfsimulator` build target（`librfsimulator.so`）在修 `bhload` segfault 那一輪只重新編譯了 `nr-uesoftmodem`/`nr-softmodem`/`telnetsrv`，漏了 `rfsimulator`——雖然原始碼已 `rsync` 過去，但沒有重新編譯，導致 PC2（Node1,3,4,5,6）、PC3（Node9~12）全部節點的 `bhload` 模組其實從未真正註冊成功，只有 PC1（Node2,7,8）的機制是真的生效。第二次的數據因此只有三分之一的節點真正受機制影響，不能代表全系統基準。
3. **第三次（本文件記錄的版本）**：確認並修復 PC2/PC3 的 `librfsimulator.so` 落後問題（三主機 `librfsimulator.so` 時間戳全部新於 `simulator.c` 原始碼），三主機皆重新編譯部署、乾淨重啟，逐一確認 `bhload` 模組在 PC1（Node2）、PC2（Node4）、PC3（Node11）都成功註冊（`module N = bhload added to shell`）後，才進行本次正式量測。

## 機制生效驗證（先於本次量測執行，涵蓋三台主機）

- 用 `tcpdump` 直接在 Node2（PC1）的 MT 迴路介面上抓包，確認 DU 端輪詢執行緒送出 `bhload query` 後，MT 端回傳真實、非零、持續累積的 MAC 統計數字（例如 `dl_rb_cum 44086 ul_rb_cum 404315`）。
- 確認 Node4（PC2）、Node11（PC3）的 MT log 都出現 `[TELNETSRV] Telnet server: module N = bhload added to shell`，且對應 DU 的 log 都有 `[Backhaul-aware PRB budget] 輪詢執行緒啟動` 訊息，三台主機的資料管線（MT 統計 → telnetsrv → DU 輪詢 → 動態縮小 PRB）確認端到端真正運作。

## 量測方法

三台主機（PC1: UE5~8、PC2: UE1~4+UE17、PC3: UE9~16）同時執行：

```bash
python3 scenarios/traffic_scenario.py --scenario R --seed 20260914 --host {pc1,pc2,pc3} --phase-duration 60 --num-phases 15
python3 iab/measure_stage.py --host {pc1,pc2,pc3} --duration 900 --interval 5 --out /tmp/stage1_{host}.csv
```

Scenario R（真實隨機場景）：面積均勻抽樣模擬細胞邊緣 UE 較多、lognormal 重尾分佈模擬真實流量需求、間歇閒置機率模擬 burst→idle→burst、持久化的每 UE 使用者 profile（heavy-streaming/light-browsing/bursty-iot）、TCP/UDP 協定混合。15 個 phase × 60 秒 = 900 秒（15 分鐘）。

**已知限制**：PC2、PC3 的 `measure_stage.py` 因為 SSH 連線與腳本路徑問題，比 PC1 晚約 1~2 分鐘才實際開始取樣；Scenario R 的流量/路徑損耗序列是連續、確定性的（由 seed + 絕對時間換算 phase index），三主機資料仍是同一組場景下的有效切片，只是相位上略微不同步，不影響本次基準數據的有效性。

**全程系統穩定性**：本次 15 分鐘量測全程，三主機所有 RAN 容器 **RestartCount 均維持不變（無新增崩潰或重啟）**。

## UE17 特別說明（使用者要求追蹤的項目）

UE17 這次呈現一個新的、更嚴重的樣貌，量測結束後立即現場複測驗證：

- **ICMP ping 現場測試：4/4 封包全部遺失（100% packet loss）**，比先前兩次量測（RTT 高但 0% 封包遺失）更差，代表這條路徑上 ICMP 探測封包目前完全無法穿透。
- **iperf3 現場測試：10 秒逾時內完全無法建立有效傳輸**，客戶端卡在連線階段。
- 但 `measure_stage.py` 量測視窗內的 145 筆取樣中，仍有 62 筆量到非零的 TCP 吞吐量（穩定落在 0.9~1.05 Mbps，數值異常平整，很可能是卡在某個很小的擁塞窗口上限反覆傳送少量資料，而不是正常 TCP 動態調整的結果），RTT/ping 則是**連續 145 次全部失敗、掛零**。
- **判讀**：這代表 UE17 目前处于「TCP 資料流勉強能擠出極少量吞吐量，但 ICMP 與新連線建立幾乎完全打不穿」的邊緣可用狀態，比 2026-09-12 稍早的量測（0.80~1.15 Mbps、RTT 639~825ms、ICMP 0% 封包遺失）明顯惡化。
- **根因判斷**：這是三台主機的 backhaul-aware 機制**這次真正全部同時生效**後的結果——Node4（UE17 直接掛載的 relay）同時要服務 UE17 直連流量、中繼 Node11（PC3）、中繼 Node12（PC3）三份負載，前兩次量測因為 PC2/PC3 的機制實際上沒有真正運作（見上方作廢說明），Node4 承受的排程壓力被低估；這次三台主機的機制都真正介入後，Node4 自己的 MT backhaul 忙碌度回饋更真實、縮減幅度更大，UE17 首當其衝變成全系統最極端的瓶頸案例。這符合 CLAUDE.md 第 2 節「多跳鏈路自我節流」理論預期的方向，但實際惡化程度（幾乎完全打不通）比理論推導的量級更嚴重，值得在論文中特別討論這個「單一節點多重負載疊加」的極端案例。

## 結論

1. **三主機全部真正生效後，JFI 與平均吞吐量反而比「只有三分之一節點生效」的第二次作廢版本更好**（JFI 0.2036→0.3303，平均吞吐量 4.53→6.45 Mbps，平均 RTT 318.10→224.23 ms）：這提示「只有部分節點做 backhaul-aware 自我節流、其餘節點完全不受限」的不對稱情境，反而可能讓受限節點的鄰居/上游更容易被不受限的節點排擠資源，全系統呈現更差的公平性與整體效能；三台主機都真正參與同一套節流邏輯後，資源分配的自我一致性反而變好。這是一個值得寫進論文方法論章節的有趣觀察，也再次凸顯了「務必確認機制在所有節點都真正生效」這個驗證步驟不可省略。
2. **UE17 成為全系統最極端的個案**，詳見上方專門說明——這不是量測工具的問題，是 Node4 三重負載疊加在機制真正生效後被放大的真實效應。
3. **深層跨主機節點（PC3 的 UE9~16）平均吞吐量仍普遍偏低（0.22~1.41 Mbps）**，符合 IAB 多跳架構＋跨主機 relay 的預期物理特性。
4. **本文件作為 Stage 2~5 的比較基準**：後續每一階都必須在**相同的（三主機皆真正生效的）backhaul-aware 機制、相同 Scenario R seed（20260914）**條件下，於 JFI、平均吞吐量、平均 RTT 三項指標上全面優於本文件記錄的數值。特別是 UE17 與 UE13/14 這類目前吞吐量或連線品質極差的深層/多重負載節點，若 Stage 2 以後的 DRL/FL 能透過感知 backhaul 緊繃程度做出更聰明的排程決策而明顯改善，會是證明優於 PF baseline 的一個直觀且有說服力的指標。
