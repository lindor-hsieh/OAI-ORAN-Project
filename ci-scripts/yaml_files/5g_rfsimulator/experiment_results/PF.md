# Stage 1 — PF Baseline 量測結果

**量測日期**：2026-09-12
**狀態**：Local-only DRL 全部停止，OAI 內建 Proportional Fairness 排程器獨立運作
**⚠️ 重要**：本次量測已套用「Backhaul-aware 動態 PRB 預算」機制（relay/access 節點依自己 MT backhaul 使用量動態縮小 DU 可用 PRB 池，實作於 `nr_dlsch_preprocessor()`，見 CLAUDE.md 第 3 節）。這份數據**不能**跟本文件更早、機制上線前的版本比較——舊版本已刪除，本文件是機制上線後的第一份正式基準，後續 Stage 2~5 都要跟**這份**數據比較。

## 量測方法

三台主機（PC1: UE5~8、PC2: UE1~4+UE17、PC3: UE9~16）同時執行：

```bash
python3 scenarios/traffic_scenario.py --scenario R --seed 20260912 --host {pc1,pc2,pc3} --phase-duration 60 --num-phases 15
python3 iab/measure_stage.py --host {pc1,pc2,pc3} --duration 900 --interval 5 --out /tmp/stage1_{host}.csv
```

Scenario R（真實隨機場景）：面積均勻抽樣模擬細胞邊緣 UE 較多、lognormal 重尾分佈模擬真實流量需求、間歇閒置機率模擬 burst→idle→burst、持久化的每 UE 使用者 profile（heavy-streaming/light-browsing/bursty-iot）、TCP/UDP 協定混合。15 個 phase × 60 秒 = 900 秒（15 分鐘），刻意拉長量測時間避免整段落在最容易連續閒置的 light-browsing profile 的 idle 視窗中。

`measure_stage.py` 已修復 PC2 先前的 ping 序列化拖慢問題（改用 `ThreadPoolExecutor` 平行送出全部 UE 的 ping），三台主機取樣覆蓋率已無量級落差。

**已知限制**：PC2 因為啟動時序（SSH 連線建立較慢）比 PC1/PC3 提早約 3 分鐘完成 900 秒量測視窗，三主機的量測時間窗沒有精確對齊到秒級；但 Scenario R 的流量/路徑損耗序列本身是連續、確定性的（由 seed + 絕對時間換算 phase index），所以 PC2 的資料仍是同一組場景下的有效切片，只是相位上略微提前，不影響本次基準數據的有效性。

**全程系統穩定性**：15 分鐘量測全程，三主機所有 RAN 容器（12 個 relay/access 節點 + Donor CU/DU + 17 個 UE）**RestartCount 均為 0**，沒有任何一次意外重啟或崩潰——這是這次上線前修復的三個 root cause bug（telnetsrv buffer overflow、CU UID 分配器耗盡崩潰、CU stale F1 association 永久拒絕）首次通過完整 15 分鐘高負載驗證。

## 結論

1. **系統穩定性達標**：這是三個 root cause bug 修復後第一次完整 15 分鐘、17 UE、三主機同時動態流量+路徑損耗量測，全程零崩潰、零容器重啟，確認這次乾淨重啟與根因修復的成果具備進行後續 Stage 2~5 量測所需的穩定性基礎。
2. **JFI（0.2584）與機制上線前的舊基準（0.2619，見 CLAUDE.md 已刪除段落記載）處於同一量級**：PF 排程器本身不考慮公平性以外的因素，backhaul-aware PRB 預算機制對 PF 而言是「輸入端的資源池縮放」，不改變 PF 演算法本身「贏者全拿」的傾向，JFI 維持在低位屬預期內。
3. **平均吞吐量（5.26 Mbps）低於舊基準（6.72 Mbps）**：這是 backhaul-aware 動態 PRB 預算機制的**預期效果**——relay/access 節點的 DU 現在會依自己 MT backhaul 忙碌程度動態縮小可用 PRB 池，機制生效後 PF baseline 本身可用的頻寬總量比機制上線前少，兩份數據衡量的本來就是不同的系統設定，不能直接視為「效能下降的迴歸」。
4. **深層節點（3-hop access，尤其 PC3 的 UE9~16）平均吞吐量普遍低於淺層節點（UE1、UE5、UE7）**：符合 IAB 多跳架構「每多一跳，可用容量被上游 backhaul 瓶頸壓縮」的預期物理特性，也正是 backhaul-aware PRB 預算機制想要真實反映的效應。
5. 本文件作為 Stage 2~5 的比較基準：後續每一階都必須在**相同的 backhaul-aware 機制、相同 Scenario R seed（20260912）**條件下，於 JFI、平均吞吐量、平均 RTT 三項指標上全面優於本文件記錄的數值。
